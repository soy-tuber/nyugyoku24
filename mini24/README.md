# nyugyoku-mini — 入玉宣言法専用ミニエンジン (Rust)

相入玉の局面だけを担当するエンジンの土台。普通の将棋エンジンのような
「評価関数 + αβ探索」ではなく、**宣言勝ちに到達できるかを証明する探索**として作っている。
手本は詰将棋ソルバー (df-pn) で、ゴールを「詰み」から「宣言勝ち」に差し替えた。

```
src/
  rules.rs   宣言判定と点数。唯一「厳密でなければならない」部分
  tempo.rs   宣言までの残り手数 T (= このエンジンの評価)
  dfpn.rs    宣言勝ちの証明探索。T を証明数の初期値に使う
  think.rs   1手の決め方 (証明 -> 安全確認 -> 競走)
  sfen.rs    SFEN / USI 指し手の入出力
  main.rs    USI エンジンと検証用サブコマンド
tools/
  compare_python.py  Python 版 (engine/) との照合
  match_python.py    Python 版との対局
```

合法手生成は [shunsai](https://github.com/sugyan/shunsai) (MIT/Apache-2.0。打ち歩詰めの除外込み) を使う。

## 動かす

```bash
cd mini24
cargo test --release                      # 規則・T・証明探索のテスト (適合性テスト46局面を含む)
cargo build --release
python tools/compare_python.py            # Python 版と宣言関連の量を照合
python tools/match_python.py 10 0.5 2 300 # Python 版 (深さ2) と対局

./target/release/nyugyoku-mini                     # USI エンジンとして起動
./target/release/nyugyoku-mini prove 20000 < sfens # 各局面で手番側の宣言勝ちを証明できるか
./target/release/nyugyoku-mini think < sfens       # 各局面での指し手
```

USI オプション: `EnteringKingRule` (`CSARule24` / `CSARule27`。floodgate は 27点法)、
`MaxMovesToDraw` (既定 512)、`ProofNodes`、`SafetyNodes`。宣言は `bestmove win`。

## 設計

### 型で守っていること

- `DeclPoints` (宣言点数 = 持ち駒 + 敵陣三段目以内) と `OwnedPoints` (所有点数 = 持ち駒 + 盤上すべて) は
  別の型。足し引きするとコンパイルが通らない。持将棋の点数は型自体を作っていない
- 宣言の結果は `DeclResult::{Win, Draw, NotAllowed}`。match の書き漏れはコンパイラが止める
- 24点法の第5項 (手数500未満) を実装している (Python 版は未実装)

### 残り手数 T (`tempo.rs`)

宣言条件 (敵陣10枚・目標点数) を埋める手段は「持ち駒を打つ (1手で枚数+1、点数不変)」と
「取り残しを運ぶ (最短手数で枚数+1・点数+駒点)」の2つしかない。
駒点は5点と1点の2種類なので、同じ点数なら手数の少ない駒から運ぶのが常に最善で、
「大駒 b 枚・小駒 s 枚」の全組み合わせを試せば厳密解になる (一般の動的計画法と全局面で一致を確認済み)。

駒のない盤での最短手数を使うので、駒取りが無い限り実際の手数の下界。

### 証明探索 (`dfpn.rs`)

- OR 節点 = 攻め方の手番 (どれか1手で届けばよい)、AND 節点 = 受け方の手番 (全応手で届かねばならない)
- 終端: 攻め方の宣言勝ち・受け方の詰みで証明。受け方の宣言・攻め方の詰み・千日手・手数上限で反証
- 証明数の初期値 = 1 + 16 x T(攻め方)、反証数の初期値 = 1 + 16 x T(受け方が宣言するまで)
- 王手されている局面は合法手 (王手の受け) を数え、0 なら詰みで確定、それ以外は
  「1 + 4 x 受けの数」で頭打ちにする (詰将棋ソルバーと同じ発想)。宣言には遠いが詰む手順を優先できる
- AND 節点の証明数は和ではなく「最大値 + 未解決の子の数 - 1」(Weak Proof-Number Search)。
  相入玉は持ち駒が多く応手が100を超えるので、和だと爆発する

**24点法の構造的な性質**: 先後の所有点数の合計は54なので、攻め方が所有31点以上なら受け方は23点以下で、
無勝負の宣言すらできない。受け方の防御は駒の取り返し・王手・詰み・手数上限・千日手に限られる。

### 1手の決め方 (`think.rs`)

1. 自分の宣言勝ち (詰みを含む) を証明できればその手 (持ち時間の4割)
2. 全候補手を「所有点数 (31で頭打ち) と T の差」で採点する。相手の応手は駒取りと
   千日手 (過去の局面に戻る手) だけ1手読み、千日手に逃げられる手は高々0点 (引き分け) とする
3. 点数の高い順に「相手が宣言勝ち・詰みを強制できるか」を調べ、最初に安全と分かった手を指す

## 検証済みのこと

- 条文から作った適合性テスト46局面 (手数条件を含む) に全件一致
- Python 版の宣言判定・点数と、相入玉ベンチマーク・適合性テスト・floodgate 実戦局の 1618局面で全件一致
- 答えの分かっている合成局面で、宣言勝ちの手順を 2〜170 展開で証明。詰みも勝ちとして証明し、
  証明手の後の全応手で再び証明できることを検算
- Python 版 (統合エンジン・深さ2) との対局: ホールドアウト10局面 x 先後、Rust 1手0.5秒、上限300手で
  **12勝2敗6分**。宣言の不正は0件 (Rust 版の `bestmove win` は毎回 Python 版の判定で検算)。
  ただし Python 版自体の絶対的な強さは不明なので、これは「今の Python 版より強い」以上の意味を持たない

## 未完成のこと (改良の優先順)

1. **速さ**: 実戦の局面で毎秒約7千展開。展開のたびに全子局面の T を計算しているのが主因。
   子の初期値の遅延計算、T の差分更新、置換表のサイズ管理 (今は HashMap で上限なし) が次の一手
2. **千日手**: 経路上の再出現を即引き分けとし、連続王手の千日手を区別していない。置換表に経路依存の値が入る (GHI 問題)
3. **局面の優越関係**: 盤面が同じで持ち駒が多い局面は T が小さい。KomoringHeights の優越関係の再利用
4. **採点が浅い**: 相手の駒取りと千日手を1手読むだけ。駒の取り合いの損得 (SEE) と王手の扱いを入れる
5. **千日手の規則**: 本来は同一局面4回だが、探索・採点とも1回目の再出現で引き分けとしている
6. **振り分け役**: 相入玉になったらこのエンジン、それ以外は NNUE 系に指させる USI 中継
7. **27点法の目的関数**: 判定は対応済みだが、指し手選択の閾値は規則に合わせて切り替えるだけで、27点法向けの調整はしていない
